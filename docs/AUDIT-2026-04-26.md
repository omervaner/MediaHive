# MediaHive Audit — 2026-04-26

Scope: `main.js`, `preload.js`, `main/`, `src/services/`, `src/components/`. Findings below
were verified by reading the code and probing call chains. Each entry cites exact file:line
locations. Severity tags: **CRITICAL** (runtime error / data loss), **HIGH** (user-visible
incorrect behaviour), **MEDIUM** (inconsistency / minor incorrect behaviour),
**LOW** (cosmetic / dead code / noise).

### 1.1 `setIsLoadingFolder` is not in scope — Escape-during-load throws — **CRITICAL**
`src/App.jsx:1456-1462`

> **STATUS:** ✅ Fixed in `ec6881e`. Hook now exposes `cancelFolderLoad`

```js
useEffect(() => {

    if (e.key === "Escape" && isLoadingFolder) setIsLoadingFolder(false);

  …

```

`isLoadingFolder` is destructured from `useElectronFolderLifecycle()`
(`src/App.jsx:304`), but the hook **does not export** `setIsLoadingFolder`

`src/components/MetadataPanel.jsx:289-344` calls `electronAPI.caption.both(...)`

### 1.4 `generateCaptionAndTags` cancellation is wired to a controller no fetch is using — **HIGH**
`main/captionService.js:232-276`

```js
const controller = new AbortController();
if (requestId) activeRequests.set(requestId, controller); // ← never connected
…
const captionResult = await generateCaption(imagePath, { ...options, requestId: null });
…
const tagsResult = await generateTags(imagePath, { ...options, requestId: null });
```

The combined helper builds its own `AbortController`, registers it in
`activeRequests`, but passes `requestId: null` to the inner calls so the inner
fetches each create their own `AbortController` whose signals are unrelated.
`cancelRequest(requestId)` aborts the wrapper controller, but neither inner
`fetch` listens to it. Cancellation only takes effect at the **boundary
between** `generateCaption` and `generateTags` (line 248: `if
(controller.signal.aborted)` check). A user pressing Cancel while the model is
mid-inference cannot stop the in-flight request.

Also the per-call `timeoutMs` from `getTimeoutForModel` is applied
independently in each inner call, so the combined operation effectively gets
**2× the configured timeout**.

### 1.5 Dataset export writes empty `.txt` files — **HIGH (matches user-reported symptom)**
`main/datasetExporter.js:92-109`

> **STATUS:** ✅ Fixed in `97ae623`. `writeFile` is now guarded by
> `if (captionContent)`. The asymmetric "tags → AI fallback" branch
> is left as-is — it's a separate design call, not a bug.

```js
if (includeCaptions) {
  const captionPath = destPath.replace(/\.[^.]+$/, ".txt");
  let captionContent = "";

  if (captionSource === "ai" && file.aiCaption) {
    captionContent = file.aiCaption;
  } else if (captionSource === "tags" && Array.isArray(file.tags) && file.tags.length > 0) {
    captionContent = file.tags.join(", ");
  } else if (captionSource === "ai" && Array.isArray(file.tags) && file.tags.length > 0) {
    captionContent = file.tags.join(", ");
  }

  await fs.promises.writeFile(captionPath, captionContent, "utf-8");
}
```

When neither `aiCaption` nor `tags` are present, `captionContent` stays `""`
and an empty `.txt` is still written. Two follow-on issues:

- The third branch (`captionSource === "ai"` fallback to tags) is
  unreachable — it duplicates the second branch's filter and is gated on `===
  "ai"`, but the prior branch only fires when `captionSource === "tags"`. The
  intent (in the UI hint at `ExportDialog.jsx:253-255`: "AI captions falls
  back to tags if no caption") is broken: when AI is selected and no
  `aiCaption`, the second branch is skipped (because `captionSource !== "tags"`)
  and the third branch is skipped (because the second already returned `""`)…
  actually trace it carefully: the chain is `if/else if/else if`, so when
  `captionSource === "ai" && !file.aiCaption`, control falls to the second
  branch (`captionSource === "tags"` — false), then the third
  (`captionSource === "ai" && tags…` — true if tags exist). So the fallback
  *does* work. But `captionSource === "tags"` has **no fallback to AI caption**,
  which is the asymmetric/inconsistent half.
- For `captionSource === "tags"` with no tags, we still write `""`.

Fix: skip the write when `captionContent === ""`, and decide on a symmetric
fallback policy (or document the asymmetry).

### 1.13 Find Duplicates always reports zero — caller invokes `duplicates:find` per-file — **HIGH (feature is non-functional)**
Found while smoke-testing the `main/ipc-duplicates.js` extraction. The IPC
handler itself is correct: given a list of fingerprints, it ensures each has
a phash and runs `findDuplicateGroups` with threshold 5. But the renderer
fires `duplicates:find` **once per file with a single-element fingerprint
array** instead of one batched call for the whole folder, so each invocation
operates on a 1-item set and `findDuplicateGroups` can never form a group.

Reproduction: load three byte-identical screenshots, click "Find Duplicates",
observe in the main-process log:

```
[duplicates] Computing hashes for 1 of 1 files
[duplicates] Found 0 duplicate groups
[duplicates] Computing hashes for 0 of 1 files
[duplicates] Found 0 duplicate groups
…
```

Five calls fire, each handed one fingerprint. UI shows "No duplicates found".
Fix the caller (search `App.jsx` / hooks for the `duplicates:find` invocation)
to send the full fingerprint array in one call. The handler does not need to
change.

This supersedes the §7 "duplicate-finder happy path" entry — that entry
probed only the IPC handler, which is correct; the bug is in the caller.

### 1.14 Metadata leaks across byte-identical files with the same birthtime — **HIGH (data corruption)**
`main/fingerprint.js:50` constructs the file fingerprint as

```
v1-{size_hex}-{createdMs}-{sha256(head+tail+size+createdMs)}
```

Inputs: file size, `birthtimeMs || ctimeMs || mtimeMs`, and a sha256 over
the first/last 64 KB plus those two scalars. Two files that share **content
and creation timestamp** therefore produce **identical** fingerprints. The
metadata DB (`main/database.js`) keys tags, ratings, and captions by
fingerprint, so collided files share a single row.

Reproduction (verified by Ömer, 2026-04-26): a folder containing three
visually-identical screenshots (likely copied via Finder's "Duplicate" /
clonefile, which preserves birthtime). Setting one to ★4 immediately shows
all three at ★4 in the UI. A folder of merely-similar but not-identical
images does not exhibit the bug. The trigger is fingerprint collision on
identical byte content + same birthtime, not visual similarity.

The IPC handlers in `main/ipc-metadata.js` and the SQL in
`main/database.js` are correct given the fingerprint contract — the bug
is in the contract itself: **the fingerprint is content-addressable, but
the renderer treats it as identity-addressable.**

Fix options, in order of severity:

1. **Quick mitigation:** include the absolute path in the fingerprint hash.
   Cheapest fix, breaks all existing fingerprints (so metadata orphans
   on upgrade — would need a migration that re-keys tags/ratings/captions
   from old to new fingerprints by file-path lookup).
2. **Proper fix:** introduce a separate `file_id` (path + size + inode or
   path + content-hash) as the primary key for metadata, and keep
   `fingerprint` only for dedup/duplicate-finder use. Bigger refactor.
3. **No-op:** document that intentional file copies share metadata, and
   point users at the duplicate finder. Cheapest in code, but it lets the
   user lose data (e.g. star a working copy → master gets the rating too).

This bug interacts with §1.13: once §1.13 is fixed and Find Duplicates
returns groups, the renderer should also be careful that "different fp" is
not the same as "different file" — and conversely that "same fp" is not
the same as "same file" once we de-collide.

### 1.15 HeaderBar overflow clips controls on narrow windows — **HIGH (usability)**
`src/components/HeaderBar.jsx`

Reported by Ömer 2026-04-26. The header toolbar (folder picker, Subfolders
toggle, recent-folders dropdown, media-type filters, zoom/render-limit
sliders, sort, layout, Filters, Export, Caption, Duplicates, Settings) lays
out its children in a single non-wrapping row. When the window is narrowed,
the right-most controls (Settings cog first, then Duplicates / Caption …)
are clipped off-screen. There's no horizontal scroll fallback, no
responsive collapse into an overflow ⋯ menu, and the toolbar isn't
scrollable via trackpad/touch gestures either. The only recovery is to
resize the window manually.

The screenshot included with the report shows the Settings cog half-cut at
the right edge with the window at ~1200px wide.

Fix options:

1. Add `overflow-x: auto` to the toolbar container so a trackpad
   horizontal-scroll exposes hidden controls. Cheapest, keeps the toolbar
   horizontal at all sizes.
2. Set `flex-wrap: wrap` and let the toolbar grow to two rows on narrow
   widths. Lets the user reach everything without scrolling at the cost of
   vertical space.
3. Implement an "overflow menu": measure available width, push less-used
   actions into a ⋯ button when they don't fit. Most polished, most code.

Likely the right call is (1) plus a sensible `min-width` so the window
can't be shrunk below the point where even scrolling becomes useless, with
(3) as a follow-up if the toolbar keeps growing.
